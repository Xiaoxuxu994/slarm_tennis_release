# 训练/验证差距：球不泛化，场景泛化

2026-09-14。`exp0908_001 / ckpt_019999`，纯像素路径（`use_ball_token: false`、
`use_ball_token_intrunk: false`），同一份权重、同一个评测器，只换场景集合。

- 验证：`ball_catch_triview_0903_2k_validation.txt` 的 100 个场景
- 训练：`ball_catch_triview_0903_2k_train.txt` 的**前 200 个**场景
  （config：`exp0908_001_eval_on_train_scenes.yml`，与原 config 只差
  `eval_annotation` 和 `exp_name` 两行）

这个 ckpt 把训练集看了约 44 遍（20000 步 × 4 卡 × batch 1 ÷ 1800 场景）。

> **这份结果推翻了 [EXPERIMENTS_AND_ERROR_BUDGET.md](EXPERIMENTS_AND_ERROR_BUDGET.md)
> 的核心结论。** 那份文档说"全部误差塌缩成 0.163 px 的视差精度"，把它当作**感知
> 极限**。同一套光学在训练场景上解出 0.045 px —— 镜头不会因为数据没见过就变糊。
> 验证侧那 3.6 倍是泛化，不是传感器。

## 二、场景重建是干净的对照组

这一节是全篇的地基。如果"训练集恰好更简单"，RGB 和深度也该更好。

```
RGB PSNR anchor        +0.004 dB
RGB PSNR farthest      −0.03  dB      训练更差
RGB p10 farthest       −0.09  dB      训练更差
ball RGB PSNR anchor   −0.11  dB      训练更差
depth absrel farthest   完全相同
```

**四项里三项训练侧反而略差。** 场景集合难度相当，差距不是选样偏差。

## 三、不是"速度难泛化"，是"球难泛化"

自然的猜测是速度比位置难泛化。**数据不支持。**

```
球的深度      3.75×      ← 最差
球的速度      2.88×
球的位置      1.39×
场景的深度    1.00×      ← 完全没有差距
```

**球的深度泛化得比球的速度还差。** 而同一个模型的场景深度一点差距都没有。所以
被区分开的不是"位置 vs 速度"，是"球 vs 场景"。

在同一个读出里，位置和速度的差距几乎相同：

```
六帧拟合   位置 1.39×    速度 1.33×
```

拟合的速度是从位置导出的，**继承了位置的泛化性质，没有额外惩罚**。

### 根因：每步的监督量差 6000 倍

训练日志里各项监督的有效值个数：

```
stream25_rgb_valid_count          4,849,664
stream25_depth_valid_count        1,613,824
stream25_semantic_valid_count     1,613,824
stream25_ms3_ball_valid_count           257      ← 球的速度/加速度/jerk
stream25_ball_depth_valid_count         136      ← 球的深度
```

**场景深度 1,613,824 个，球深度 136 个，差 11866 倍。**

再叠上球本身的尺寸：直径 2.66 px、面积约 5.6 px，占 320×240 的 **0.007%**。
全图 PSNR 根本看不见球；而房间每个场景都一样，本来就没什么可记的。

**每个场景真正变化的只有球的轨迹，那正是被背下来的东西。**

### 被记住的是"球会去哪"，不是"球长什么样"

```
ball IoU anchor    （观测窗口内 0-15）   +0.009    几乎无差距
ball IoU farthest  （外推 22-24）        +0.192    差很多
```

外推段差、观测段不差 —— 这是轨迹记忆的直接签名。

## 四、六帧拟合 vs MS3 头：结论

```
                  验证     训练    差距
MS3 头            0.098   0.034   2.88×
六帧拟合           0.106   0.080   1.33×
```

**① 部署口径下两者等价。** 验证集上 0.098 vs 0.106，差 8%，以 N=100 的样本量看
在噪声内。**不要因为"几何更可靠"就期待拟合在验证集上更好 —— 它不更好。**

**② MS3 头在训练集上的 2.4 倍优势，全部是记忆。** 训练 0.034 vs 0.080，到验证集
优势完全蒸发。

**③ 几何读出确实抗过拟合，这一点用数据立住了。** 拟合 1.33×、MS3 头 2.88×；而
逐帧误差的 const/scatter 几乎不随训练/验证变化（1.12× / 1.20×）——
**渲染出来的球心本身不记忆，记忆发生在它之后的回归头里。**

**④ 但两者被卡住的原因不同，这才是要紧的。** 把白噪声界算出来对照
（`σ_v = σ_p /(Δt·√(n(n²−1)/12))`，n=6、Δt=0.1 s，逐轴 σ 由 scatter 的 3D 模
除以 1.596 得到，再乘 1.538 换回中位模长）：

| | 验证 | 训练 |
|---|---:|---:|
| scatter | 0.018 | 0.015 |
| 白噪声界 | 0.041 | 0.035 |
| 六帧拟合实测 | 0.106 | 0.080 |
| 高于界 | 2.6× | **2.3×** |
| MS3 头实测 | 0.098 | **0.034** |

- **六帧拟合在训练集上仍然高于白噪声界 2.3 倍。** 它的瓶颈不是泛化，是逐帧误差
  的时间相关性 —— 加数据救不了它。
- **MS3 头在训练集上恰好打到白噪声界（0.034 vs 0.035）。** 在它记住的数据上，
  它把渲染球心里的信息榨干了；它的瓶颈纯粹是泛化。

**两条路的终点是同一个数 ~0.035 m/s，拦路的问题不同。** 0.035 m/s × 1.005 s
= 3.5 cm，远在 11.96 cm 容差内。

## 五、两个必须分开的问题

| | 问题 | 证据 | 加数据有用吗 | 换读出有用吗 |
|---|---|---|---|---|
| **A** | 渲染读出的**时间相关误差** | 训练侧也高于白噪声界 2.3× | ❌ | 也许（见下） |
| **B** | **泛化差距** | MS3 头 2.88×、拟合 1.33×、场景 1.00× | ✅ | ❌ |

**A 在训练集上同样存在，所以它不是泛化问题。** B 只能靠数据。两者互不相干，
可以并行修。

A 的候选机制还没判定。已知：

- **不是因果信息不对称。** `pixel pos err f0 / f15` 两侧都基本持平
  （验证 0.035/0.032、训练 0.037/0.028），没有单调斜坡。
  （ball token 的 prefix 有强斜坡，那是 ball token 独有的。）
- **不是 Z² 尺度误差。** 球从 Z≈5.6 走到 4.0，`Z²` 变 2 倍，若误差 ∝ Z² 则
  f0 应约为 f15 的两倍。实测持平。
- **剩下亚像素量化相位。** 未验证。判决实验：把逐帧误差对 `frac(u), frac(v)`、
  `Z`、帧序号分别回归，看谁解释得多。约 30 行，纯 numpy，不需要 GPU。

## 六、对任务的影响

容差 **11.96 cm**：

```
验证   med 0.108（压线）    p95 0.252（超 2.1 倍）
训练   med 0.038            p95 0.081（仍在容差内）
```

**训练集上连第 95 百分位都能接住。** 且 p95/med 两侧接近（2.33 vs 2.13）——
**整个分布平移，不是几条离群场景拉的**。
